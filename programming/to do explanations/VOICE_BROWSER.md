# The voice browser ("show voice")

**Status: BUILT.** Say **"show voice"** anywhere. It opens on the window you said
it in. Say **"show voice <words>"** to open on a search, or **"show <category>
commands"** ("show music commands", "show Claude commands") to open on one group.

## Why it was rebuilt

Jamie, 2026-10-07: *"If I say 'show voice,' it doesn't open based on the context
… it's just this giant list of commands that is illegible to me … the search
sucks."* The old picker (`ShowVoiceTagPicker` + `VoiceCommandTagBrowser.ahk`,
now in `AutoHotkey/Archive/`) had four structural faults:

| Fault | Evidence | The fact that already existed |
|---|---|---|
| Groups were **guessed** tags | "claude" held Venmo, pirate bay, "Dylan"; "debug" had 1,047 rows | none: categories had to be curated |
| **One row per Choice value** | 6,560 rows for ~1,850 real commands | the grammar dump has each template once |
| **Ignored the window** | bare "show voice" had nothing to go on | the grammar dump records every command's exe/title scope |
| **No idea what she says** | everything ranked alphabetically | the utterance logger records every recognition with time + window (31 days) |

So most of v1 is a JOIN, not new data.

## What it shows

Root, top to bottom:

1. **Matches for "…"** — only when opened with words. Literal word hits first,
   then meaning-search hits, then a divider and **＋ functions that do this but have
   no voice command yet** (Enter opens that function in show fun to add one).
2. **Here · <place>** — commands scoped to exactly this window (e.g. Google Docs).
3. **All of <app>** — commands for the whole app (e.g. all of Chrome), when the
   window also has a narrower scope.
4. **Your usual here** — what she says most *in this place*, ranked by count then
   recency. Falls back to "Your most used" anywhere when nothing is logged here.
5. **Said recently** — newest first.
6. **~15 categories**, each sorted most-said first, then A–Z.
7. **Search by meaning…** — type a description; the viewer relaunches on Matches.
8. **⚙ Settings** — `voicebrowser.show_builtins`, `enter_fires`, `usual_count`,
   `recent_count`.

Each command row: **phrase** (in the wording she actually uses — `(terminate |
escape | exit | cancel)` shows as **escape**), **what it does**, **uses**. The right
pane previews where it works, how often and how recently she said it, the values
she says ("watch jujutsu · watch warcraft"), its function and file.

Spoken-list commands (`watch ‹watch show›`) are ONE row; Enter drills into the
values, most-said first (and query-matching first under Matches).

**Actions:** Enter = say it for you in the window you came from (Dragon mimic via
`DragonMimicAsync`), or copy it when it needs words from you. Anything
destructive-sounding (shut down, restart, close, delete, clear, cancel, sleep, …)
is never fired from here, only copied. `N.2` copy · `N.3` open in show fun · `N.4` open
the rule file. Typing filters the whole catalog (flat search index; each command
appears once, under its category).

## How it works

```
Caster "show voice [<words>]" / "show <category> commands"
  → OpenVoiceBrowser(query, jump)          Helpers/VoiceBrowserMenu.ahk
      captures the foreground window (exe, title, hwnd) BEFORE anything opens,
      writes it + the request to a unique temp file (titles can hold anything),
      closes any open browser (its "Here" belongs to another window),
      LaunchMillerViewer → Scripts/VoiceBrowserViewer.ahk (own process)
  → ONE shell-out: voice_catalog.py rows --win-file <file>
      → TSV: every command, already ranked for this window
  → everything else is in memory (only `values <id>` shells, on drill)
```

`Scripts/voice_browser/voice_catalog.py` joins:

1. **What is live + where** ← `~/.claude/context/voice_grammar_dump.json`
   (regenerated by Caster on every rule reload / "make catalog").
2. **What it does** ← rdescripts (the `voice_commands_by_tag` collector) + the
   generic command store.
3. **Which group** ← `AutoHotkey/INIDATA/voice_categories.json`.
4. **What she says, where** ← `Scripts/dictation_logger/dictation_log_*.jsonl`,
   each utterance matched to the spec that would have fired by `voice_index`'s
   spec→regex compiler (the collision checker's). The most specific match wins
   (literal words beat dictation slots; scoped beats global). Results are cached
   per (text, place) in `~/.claude/context/voice_usage_match_cache.json`.

The catalog (`~/.claude/context/voice_catalog.json`) **rebuilds itself** when any
input is newer (dump, categories, store, any rule file, the module). No hook to wire.
Measured: build 0.7 s; a `rows` call 0.2 s; with a query ~1.7 s (qmd daemon).

### Places

A **place** is a Dragon scope: the most specific (exe, title) pair matching a
window — context JSONs with a `caster_scope` first (so they carry her names:
"Google Docs", "Reading Room"), then every other scope in the dump
(`place_names` in the categories file renames the odd ones, e.g. `voice -` →
"Google Voice"). "Here" and usage bucketing use the same function, so they can't
disagree about where a window is.

**The context detector decides, not just the title** (2026-10-10). A Spotify tab
playing a song is titled "Song • Artist - Google Chrome", so a title-only match
called it plain Chrome. `OpenVoiceBrowser` now records `DetectContextChain(true)`
(deepest first, e.g. `spotify,chrome`; URL-aware) as line 6 of the target file, and
`effective_title()` appends the first chain context's `caster_scope.title` to the
window title before any place or "here" test. Logged utterances have no chain, so
there only contexts decidable by `title_regex` alone apply. A title that already
resolves to a title-scoped place is left alone (an Instagram "A • B" title never
gains Spotify's scope).

Caster had the same blind spot: both Spotify rules were scoped `title="Spotify"`,
so Dragon didn't hear them in a playing tab. Fixed the same day with
`caster_scope.title_regex` / `title_exclude` in `spotify.json` and
`generic_command_store.title_context()` (caster-voice skill,
`references/context-scoping.md`). Those rules now dump as chrome +
`LogicAndContext`, and their `conditions` entries say "Spotify". For a rule with a
condition, the condition alone decides "here", never the dump's outer exe.

Caster's CCR merge rule (`PreparedRule`, a FuncContext wrapper) counts as
everywhere. Other function-context rules get their place from `conditions`
(see Phase 2).

### Hidden by default

The 392 "enable/disable <rule>" grammar-activator commands, the per-rule
"X Commands" probes and the generated "materializer … test" probes, and Caster/Dragon
built-ins no rule file of hers defines. `voicebrowser.show_builtins` shows them.

## Categories: curated, and Claude's job

15 groups, in menu order: Windows & screens · Opening apps & folders · Typing &
editing text · Mouse, clicking & lists · Chrome & websites · Messages & people ·
Music & video · Reading & books · Journal & writing · Focus, time & logging ·
Claude & AI · Lists, stacks & clipboard · Coding & terminal · Art, images & play ·
Voice, Dragon & setup.

Assignment precedence: `phrase_rules` (regex, optionally per file) → `by_file`
(rule file) → `helper_rules` (regex on the AHK helper that owns the function, for
generic-store commands) → `default`. On 2026-10-07: 973 by file, 118 by phrase, 56
by helper, 5 default (genuine setup commands).

**Jamie does not confirm categories per command** (her decision, 2026-10-07). When
Claude adds a command it adds the mapping; `voice_catalog.py uncategorised` is the
check. This rule lives in the caster-voice skill.

## Search

- **Typing in the filter**: instant, across the whole catalog (phrase, aliases,
  description, values she says, function).
- **Spoken / "Search by meaning"**: `_literal_rank` (≥60% of the non-filler words,
  phrase hits weighted, a spoken-list value only counts as a WHOLE value, and a
  free-dictation command's "said" is excluded because it is prose) then
  `meaning()`: the qmd `functions` collection through the warm MCP daemon
  (`localhost:8181/mcp`, hybrid + rerank, ~1.5–5 s), falling back to a cold
  `qmd vsearch` CLI if the daemon is down. A function hit maps to every command
  calling it; a voice-doc hit (`say: <spec>`) maps by spec.

Two noise sources found while tuning, worth knowing: the Caster format command
(`‹capitalization› ‹spacing› ‹words›`) has hundreds of spoken values and her prose
in "said", so it matched every query until both were neutralised.

## Phase 2 (built 2026-10-07, same day)

- **Function-context rules** (81 commands: dictation box, ListNav, click hints,
  Miller voice, Claude sends, writing boxes, grab numbers) are scoped by a Python
  predicate, so there is no exe/title to read — a reboot could never fix them.
  `conditions` in `voice_categories.json` says, per rule name, where each one holds
  in window terms (`any`, OR'd), or marks it `transient` (an overlay state: shown
  with its label, never under Here). `listnav: true` expands to every context with
  ListNav selectors. In a writing box, Here now lists rate/tag/title/mark; on Google
  Voice, the jump/next list commands.
- **Exact usage attribution.** `dictation_logger.py` now records `rule` (and
  `grammar`) from Dragonfly's `on_recognition(words, rule, node, results)`, and
  `rule: ""` for plain dictation. The catalog uses it to match only within the rule
  that fired (scope checks moot) and to skip dictation entirely; older records
  still fall back to word matching. **Live after the next `reboot caster`.**
- **Spoken-list dispatchers.** `grammar_dump.py` now writes identifier-shaped
  Choice values (`<win_snap>` "snap twin" → its function). The catalog keeps the
  ones naming real functions (`choice_fns`); meaning search maps a function hit back
  to the exact phrase (shown first under Matches as "snap twin — runs X"), and
  drilling into values shows what each runs. **Live after the next `reboot caster`**
  (the dump module is cached). Verified against a simulated dump.
- A–Z ordering sorts on the words, so `(find/jump [to]) next` files under f.

**Verified live after the reboot (2026-10-07 10:33):** the dump carries values for
174 spoken lists; the logger writes `"rule": "claude commands"` etc. "snap window
to the left" → **snap left** (runs SnapPrimaryLeft) heads Matches; values that
still need another slot ("open ‹program› top") are dropped from the exact-phrase
rows rather than shown unsayable.

## Phase 3 (built 2026-10-07)

- **Descriptions for store commands.** A command with no rdescript but an AHK
  function borrows the function's sidecar `summary`, de-slashed ("Switch to / open /
  jump to the previous…" → "Switch to the previous…"). Blank descriptions fell from
  388 to 358 — the rest are Caster's own VS Code / CCR rules, which have nothing to
  borrow.
- **Extra places** (`extra_places` in the categories file): Typing box (978 logged
  utterances), Writing box, Entry title box, Dragon dictation box. Before, every AHK
  window shared one "AutoHotkey" bucket, so "Your usual here" could not tell a
  writing box from a menu.
- **Stop-hook guard.** `voice_catalog.py check` (run by `caster_ahk_verify.py` as
  `voice_categories`, WARN-only, on any rule-file / store / categories change)
  lists commands that fell to the default category and function-context rules with
  no `conditions` entry. This is what enforces "Claude curates categories".
- Measured in real use: window open 0.2–0.3 s (Mcp/perf), data 0.2 s; Enter's
  Dragon mimic path has 23 clean runs in the log.

## What the rule logging taught us (2026-10-07)

- **An empty `rule` is NOT reliably dictation.** Natlink sometimes notifies a real
  command without its rule ("sleepy", "again do" both arrived with `rule: ""`), so
  the catalog treats `""` as unknown and falls back to word matching. Skipping it
  would have dropped real uses.
- **CCR commands log as `Repeater<N>`** but the dump calls that rule
  `PreparedRule`; the catalog aliases one to the other.
- **The format command's uses are real**: "say planned", "sing a lot of the leaves…"
  arrive under the CCR rule. That is Jamie dictating through Caster's `say`/`sing`
  formats, not misattributed prose.
- The left-pane horizontal scrollbar was the menu's fault, not the engine's: root
  rows had 2 columns under a 3-column header, and the engine fits only the columns
  the rows carry. Sections now carry an explicit empty third column.
